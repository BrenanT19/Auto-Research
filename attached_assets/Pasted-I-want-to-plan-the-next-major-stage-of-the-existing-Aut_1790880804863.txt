1. VEHICLE DATA HIERARCHY
--------------------------------------------------

Plan a scalable vehicle information architecture based roughly on:

Manufacturer
→ Model
→ Generation
→ Model Year
→ Trim
→ Powertrain / configuration

The architecture needs to handle cases where:

- one model has many generations
- generations span multiple model years
- specifications change during a generation
- one model year has multiple trims
- trims may have different engines, motors, batteries, transmissions, drivetrains, wheel/tire packages, towing capacities, etc.
- one engine/powertrain may be shared across multiple trims
- a reliability issue may apply only to certain years, engines, transmissions, drivetrains, batteries, trims, or production ranges
- a recall may apply to a model population but not necessarily be open on an individual VIN
- maintenance information may vary by engine/powertrain/configuration
- electric vehicles require different fields from ICE vehicles
- hybrids and plug-in hybrids need to be represented correctly
- historical vehicles may eventually be supported

Avoid unnecessary overengineering, but do not structure everything as independent flat vehicle cards if that will make real automotive data difficult to maintain later.

Explain how the existing 13 demo profiles could eventually fit into this hierarchy without breaking current routes unnecessarily.

2. BROWSE CARS EXPERIENCE
--------------------------------------------------

Plan improvements to the existing Browse Cars page while preserving its current visual design.

SEARCH:

Replace the current basic text filtering experience with an autocomplete/search-suggestion system.

Example:

User types:
Tes

Possible suggestions:

Tesla
Manufacturer

Tesla Model Y
Model

2024 Tesla Model Y Long Range
Vehicle / configuration

Suggestions should be generated from the available vehicle dataset, not hard-coded search phrases.

Plan for:

- Enter selection
- Escape to close
- appropriate no-results state
- clearing the query
- closing suggestions after selection
- responsive/mobile behavior
- accessible semantics

Do not require a production search service yet.

FILTER HIERARCHY:

The Browse Cars filters should become dependent/cascading rather than independent.

Preferred user-facing hierarchy:

Manufacturer
→ Model
→ Generation / Model Year
→ Trim

The underlying data may separate Generation and Model Year if that is cleaner.

Example:

If Manufacturer = Tesla,
Model should only show Tesla models available in the dataset.

If Model = Model Y,
Generation and Model Year should only show applicable options.

If Model Year = 2024,
Trim should only show trims/configurations available for that selection.

Changing an earlier filter should automatically reset incompatible downstream filters.

Example:

Tesla
→ Model Y
→ 2024
→ Performance

If the user changes Manufacturer to Ford, incompatible Model, Year, Generation, and Trim selections should reset safely.

MODEL YEAR:

Replace the manually typed year field with a dropdown/select control.

Do NOT create hundreds of meaningless years with no matching vehicles.

For now, derive available years from the current dataset.

The architecture should nevertheless support much older vehicles in the future as the database expands.

CLEAR FILTERS:

"Clear all filters" should only appear when the user actually has an active search/filter/sort override.

Clicking it should:
- clear search
- reset manufacturer
- reset model
- reset generation/year
- reset trim
- restore default sorting
- close search suggestions
- return Browse Cars to its default state

After everything is reset, the Clear All control should disappear.

"Most popular" may remain the default sort and should not by itself count as an active filter.

Keep the existing sorting concepts for now:
- Most popular
- Estimated reliability
- Annual ownership cost

Do not redesign the vehicle cards during this planning stage.
